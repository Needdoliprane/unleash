# Spécifications des dix espaces GUI

Contrat commun R3–R5 : projections du même backend, cursor et expected_revision ; erreurs et états selon [IPC](../architecture/ipc-and-apis.md). Tous écrans : vide, chargement, données partielles, erreur, déconnexion, droits insuffisants et reprise. Les 58 groupes de parité restent dans ces dix espaces ; aucune action de lecture ne lance une génération, un apprentissage ou un test coûteux.

## Écran mission représentatif

Le haut affiche nom, objectif, owner user ou agent et condition de terminaison. Une bande de synthèse présente mode, étape/bloc, prochaine décision, derniers faits et alertes. Le centre contient procédure et données/lots ; les panneaux Git et agents apparaissent lorsque le travail les utilise. L’inspecteur ouvre source, ligne, agent éventuel, preuve ou décision sans perdre la mission. Une mission mécanique ne montre pas un agent fictif « en réflexion ».

Actions principales selon état : poursuivre une mission prête, répondre à une demande, résoudre une dépendance, inspecter une issue incertaine. « Forcer terminé » n’est pas un bouton qui contourne les règles ; modifier done est une révision explicite soumise aux frontières de workflow.

## Écran Settings

Les profils LM Studio, Ollama, llama.cpp et compatibles restent distincts par dialecte. Les clés sont optionnelles selon l’authentification qualifiée ; lorsqu’elles sont nécessaires, elles sont ajoutées/remplacées dans une surface protégée. Connexion, inventaire, capacités et probe de génération sont des phases séparées ; aucune n’est relancée automatiquement au rafraîchissement. `local_only` exige une preuve de placement applicable, avec état inconnu conservé et aucun fallback cloud implicite. Voir [local-models](../specs/local-models.md).

Les scopes sont décrits dans le langage utilisateur. Le mode AI-Guard affiche garanties présentes/manquantes. Le mode d’isolation du projet (`standard` ou `strict`, Q-05, [frontières de sécurité](../architecture/security-boundaries.md)) est affiché avec ses garanties présentes/manquantes ; `standard` est signalé non confiné pour le code lancé sous le même UID. Le pool global compte invocations agentes, workers de replay et probes fournisseur, sans exemption : défaut 5, borne dure 50. L’écran affiche la réserve de contrôle (souple d’une unité par défaut, dure en option si C ≥ 2 ; Q-15, [ADR-13](../architecture/adr/ADR-13-scheduler-budget.md)) et, pendant une baisse, requested_limit en attente et effective_limit, jamais « limite 5 active » avec 50 unités ; une demande de 51 est rejetée même si le widget devrait la prévenir. Réservations navigateur et limites d’inférence locale restent distinctes et visibles.

## Parcours guidé et choix du mode

Dans Overview, le parcours présente résultat/template exact → sources → données/paramètres → mode → modèle si nécessaire → permissions → aperçu. Il conserve le draft à chaque sauvegarde sous révision. Le modèle ou le nombre d’agents n’est pas la première question. Les valeurs recommandées sont modifiables, sans perte des détails avancés. L’aperçu distingue ressources réutilisées, agrégats locaux à créer, futures actions et inconnues ; ApplyGuidedSetup ne déclenche pas StartRun.

Le choix replay affiche forbidden et absence d’appels modèle ; supervised affiche blocs, checkpoints/exceptions déclarés et budgets de leader_decision. Une décision du leader cite rapports et assertions ; les logs seuls ne valident pas la réussite. La réparation est une opération séparée, possible sous politique préautorisée, et ne remplace pas la version du run en cours. Les autorisations déjà couvertes ne sont pas redemandées à chaque étape. [Expérience guidée](guided-automation-experience.md).

## Mesure

F014 couvre navigation et design ; F015 vérifie équivalence terminal. Les charges avancées R2 restent requises : vingt leaders, repository multilangage, document inaccessible, branche non intégrée et appel interrompu. Les parcours guidés ajoutent mission sans dépôt/agent, CSV invalide, modèle local de placement inconnu, replay sans fournisseur et supervision avec effet inconnu. Chaque écran doit expliquer ces cas sans imposer les logs bruts. Ce sont des scénarios à vérifier, pas des résultats de tests exécutés ici.

## Contrat miroir terminal

Chaque action et information de ces écrans possède un parcours TUI répertorié dans [gui-tui-parity](gui-tui-parity.md). Cela inclut Workflow Editor, Skill Studio, rôles, réglages, OAuth, inspection de contexte et contrôle de terminaux. Les prévisualisations se traduisent en données structurées, références et accès à l’original ; cette adaptation ne permet pas de retirer la sélection, l’édition ou les commandes métier. Les décisions d’autorité restent dans le backend commun.
