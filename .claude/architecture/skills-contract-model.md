# Modèle des skills, rôles, contrats et preuves

## Entités et responsabilités

| Entité | Contenu et identité | Responsable |
|---|---|---|
| Skill | Instructions réutilisables, schémas d'entrée/sortie, contrat, outils demandés, ressources, provenance ; version immuable | N+2 responsable, rédaction délégable à N spécialisé, utilisateur éditable |
| Rôle | Objectif, responsabilités, skills exacts, politique de modèle, capacités/permissions demandées, contrats, contexte et scope | N+1 compose et réutilise ; N+2 organise ; utilisateur peut éditer |
| Agent | Identité logique et liens organisationnels ; instancie un rôle pour une mission | Harness après commande autorisée |
| Session | Historique durable, checkpoints et références de contexte d'un agent | Service de sessions |
| Worker | Processus Rust éphémère exécutant une invocation | Scheduler et supervision |
| Contrat | Prédicats typés et allowlist de validateurs sur entrées, sorties, actions et traces | Moteur de contrats, contenu versionné |
| Workflow | Programme déclaratif de contrôle et de terminaison | Compilateur puis moteur déterministe |

Le Role Registry est une capacité de premier ordre, distincte conceptuellement du Skill Registry même si les tables, digests et composants de stockage sont partagés. Les namespaces sont séparés ; un ID de rôle ne peut être résolu comme ID de skill. L'identité d'une entrée de registre est le tuple (`entry_kind`, `scope_kind`, `scope_owner_key`, `entry_id`) et celle d'une version y ajoute `version` ([ADR-06](adr/ADR-06-skill-role-registry.md), R7). `scope_owner_key` vaut `global` pour la portée globale et l'owner du namespace sinon ; il n'est jamais nul, car SQLite tient deux NULL pour distincts dans une contrainte d'unicité. Les schémas sont [skill.schema.json](../schemas/skill.schema.json) et [role.schema.json](../schemas/role.schema.json). Dans ces schémas, une référence qualifiée s'écrit `{id, version, scope{kind, owner_id}}` ; `owner_id` nul (portée global) correspond à `scope_owner_key=global`, et `entry_kind` est fixé par le champ référent (`skills` et `entry_skill` : skill ; `contracts` : contract ; `role_ref` : role). Le `namespace_ref` d'une source `registry_version` d'un reçu de découverte vaut ce même `scope_owner_key`.

Un rôle composé déclare `entry_skill`, une référence exacte qui doit appartenir à `skills`. Les inputs et outputs d'une tâche suivent le contrat de cette entrée. Les autres skills restent des compétences liées ; leur utilisation éventuelle est tracée et bornée sous leurs contrats et ne change pas implicitement le schéma de sortie de la tâche. Un slot tardif vérifie la compatibilité du contrat de cette entrée avant de lier le rôle.

## Algorithme V1 de compatibilité d'un slot tardif

Le profil contractuel exigé par le slot est un objet immuable identifié par id/version/digest. Il contient digests des schémas d'entrée/sortie, liste de règles obligatoires avec leur digest, catalogue de validateurs autorisé et versions de compilateur/évaluateur. Le manifest d'exécution épingle ces versions **avant** la première évaluation, pas seulement dans son rapport final. Les schémas et règles viennent des bundles autorisés réellement chargés, pas de digests déclarés par le modèle.

1. Résoudre le profil exact, le rôle exact et son unique `entry_skill` exacte membre de `skills`. Une entrée absente, ambiguë ou non membre refuse le binding entier.
2. Calculer les digests des schémas d'entrée et sortie du skill d'entrée, avec la canonisation du profil. Les comparer par égalité exacte aux digests exigés. V1 ne résout ni inclusion générale de JSON Schema ni équivalence déduite de prose ; un schéma logiquement équivalent mais d'octets canoniques différents est refusé.
3. Pour chaque règle obligatoire du profil, exiger le même ID et le même digest de règle dans le contrat candidat. Retrait, remplacement, changement de phase, sévérité ou politique d'inconnu refuse la compatibilité. Les règles supplémentaires ne sont permises qu'avec nouveaux IDs, validateurs allowlistés du profil, sévérité obligatoire et conjonction au verdict existant ; elles peuvent réduire l'ensemble des sorties acceptées, jamais l'élargir.
4. Vérifier niveau du rôle, scope, capacités demandées sous le plafond du slot et outils requis. Les capacités effectives sont l'intersection avec les grants actuels. Si un outil obligatoire perd une capacité nécessaire, le binding échoue ou l'action est bloquée après révocation ; le système ne prétend pas que l'outil reste disponible.
5. Écrire atomiquement le manifest append-only, les versions/digests de rôle et skills, les versions compiler/evaluator/catalogue déjà sélectionnées, le rapport de compatibilité et les événements RoleBound/SkillBound. Une course avec activation est tranchée par révision : aucune activation ne peut observer un binding partiel.

Au crash/reprise, les mêmes versions d'évaluation sont utilisées. Une nouvelle version du catalogue n'est pas substituée à celle engagée ; si l'ancienne est indisponible ou révoquée pour sécurité, la continuation bloque et exige traitement explicite. Une révocation de permission reste immédiate au broker. Un sous-typage sur profil plus riche pourra être une alternative d'ADR ; ce dossier choisit l'égalité exacte pour V1 et n'annonce pas un solveur général.

## Résolution et pinning

Une recherche non qualifiée consulte d'abord repository, puis projet, puis global. Elle retourne tous les candidats autorisés avec portée, version, statut, provenance et raison de classement ; le choix prioritaire reste visible. Une référence pleinement qualifiée porte ce tuple d'identité et ne tombe jamais silencieusement sur une autre portée. Deux candidats également prioritaires provoquent `AMBIGUOUS_REFERENCE`, pas un choix au hasard. Une portée étroite n'élargit pas les droits du lecteur.

Avant le run, le système épingle le workflow et résout ses bindings fixes en un manifest avec digests. Les slots tardifs explicitement déclarés peuvent recevoir un rôle par `BindRole` avant leur première activation, sous plafond de capacités et contrat compatible. Le manifest s'étend alors par événements append-only `RoleBound`/`SkillBound` ; un binding engagé ne peut changer, même au prochain appel LLM ou à l'itération suivante. Cette souplesse préserve le choix N+1 d'une compétence créée pendant la mission sans modifier les tâches déjà engagées. La version du rôle référence des versions exactes de skills ; elle ne contient pas `latest`. Les alias facilitent l'édition d'un draft et la sélection d'un binding encore vierge, puis disparaissent du manifest effectif. Le prompt, les outils déclarés, les schémas et l'ACL déclarée appartiennent au même bundle versionné. Une modification de l'un produit une nouvelle version de l'ensemble.

L'autorisation effective est calculée séparément à chaque action : intersection des grants actuels de l'utilisateur/projet, de la mission, du rôle, du skill, du scope et des politiques de sécurité applicables. Un auteur N+2 peut demander davantage ; il ne peut pas s'accorder davantage. Les permissions révoquées cessent d'être effectives immédiatement pour les nouvelles actions. Leur retrait est journalisé ; les octets du bundle épinglé restent inspectables.

## Contrat observable

Le contrat contient des entrées/sorties de forme JSON, des capacités requises et des règles identifiées. Chaque règle possède `id`, `validator`, `phase`, `parameters`, `severity` et `on_unknown`. Le catalogue livré en V1 est `validator-catalog` v2, fermé, de 13 validateurs ([ADR-07](adr/ADR-07-contract-enforcement.md), R7) : `json_schema`, `artifact_present`, `artifact_digest`, `path_within_scope`, `git_snapshot_matches`, `observed_process_exit`, `test_observation_matches`, `claim_evidence_links`, `diff_within_scope`, `integration_observed`, `discovery_receipt_present`, plus `test_execution_matches` et `claim_predicate_matches` selon [les règles R6](../specs/contract-enforcement.md). La v1 en est le sous-ensemble historique des 11 premiers et reste chargeable pour un profil qui l'épingle. Ajouter un validateur requiert du code interne Rust et une revue du catalogue ; aucun script libre n'est compilé depuis le Markdown.

Le résultat d'une règle est `pass`, `fail` ou `unknown`. Un code de retour nul prouve seulement que la commande observée a fini avec ce code sous l'environnement enregistré. Le validateur historique de tests peut exiger un parseur et un nombre de cas ; il ne désigne pas une commande exigée. Pour cette exigence, `test_execution_matches` lie l'observation à `ExpectedTestExecution` scellé par le harness avant dispatch depuis une version acceptée du plan/contrat/mandat. La règle nomme un slot littéral ; la sortie modèle ne choisit jamais l'attendu. Aucun contrôle n'établit la correction future du logiciel. Une règle de scope porte sur les ressources contrôlées et leurs identités canoniques, pas sur une promesse textuelle du worker.

Les assertions qualitatives telles que maintenabilité, adéquation métier ou clarté sont des critères de jugement. Le N+1 peut les accepter, demander correction ou escalader avec justification et preuves. Le moteur n'en fait pas des garanties par substitution d'un autre LLM. Un évaluateur supplémentaire est possible si le workflow ou la politique le demande ; il n'est pas requis par défaut.

## Observation, claim et judgment

`Observation` porte producteur authentifié, action, snapshot, scope, horodatage observé, digest d'artefact, état de résultat et méthode de collecte. `Claim` porte auteur, proposition et références invoquées. `Judgment` porte décideur, décision, evidence bundle, révision examinée et justification partageable. Ces objets restent distincts et reliés. Une contradiction observable établie ne peut pas être écrasée par le jugement ; la décision doit la traiter.

Le [format Claim V1](../schemas/contract-claim.schema.json) distingue proposition qualitative et deux prédicats fermés versionnés : `process.exit_code` et `test.expectation_satisfied`. Le sujet est exact : identité/révision, scope/révision et snapshot typé id/digest. La [projection de test](../schemas/test-execution-observation.schema.json) vient d'un adaptateur authentifié ; les liens client ne créent aucune observation. `claim_evidence_links` contrôle seulement les liens. `claim_predicate_matches` compare une valeur typée à la projection du binding attendu ; une prose qualitative ou une preuve insuffisante reste unknown. Une vérité exigée par le profil a une règle obligatoire, prépubliée et conservée par digest ; aucun juge LLM n'est ajouté pour suppléer le vocabulaire.

L'[attendu d'exécution](../schemas/expected-test-execution.schema.json) précise outil, argv, cwd canonique, environnement pertinent, suite, parseur et politique de résultat. Le compilateur dérive les slots requis des règles. L'admission matérialise puis scelle leur binding à un sujet et une action avant l'effet ; absence de source autoritaire bloque. Ces références entrent dans le manifest avec leurs digests. Reprise et retries conservent l'attendu, et le serveur sélectionne la tentative courante à la révision examinée, jamais celle dont le résultat est le plus favorable. Les invariants, résultats pass/fail/unknown et limites de collecte sont définis dans [contract-enforcement](../specs/contract-enforcement.md).

Un evidence bundle est un instantané adressé par contenu de références autorisées, avec statut de fraîcheur, lacunes et contradictions. La création du bundle n'oblige pas à dupliquer des logs sensibles. Une décision examine un bundle précis ; si ses préconditions ont changé, le harness refuse `STALE_EVIDENCE` ou demande une nouvelle décision. Les modèles ne fournissent pas leur raisonnement privé ; seuls résultats, justification utile, entrées effectivement envoyées et références d'action sont conservés.

## Recherche avant création

Le harness expose une opération de découverte typée portant `resource_kinds`, requête, workspace, snapshot et scope. Le reçu durable contient candidats trouvés, sources consultées, fraîcheur, limites et ACL ; une absence de résultat n'est pas une preuve d'absence de doublon. La décision associée vaut `reuse` ou `create` selon l’identité cible, avec stratégie explicite, références et justification. Cette procédure couvre helpers, fonctions, classes, composants, API, contrats, tests, skills, rôles, automatisations et ressources techniques, selon la [liste canonique F009](../specs/shared-knowledge.md#discovery--invariant-transversal).

Le contrat peut exiger un reçu antérieur à la création identifiable ou à la clôture. Le moteur vérifie l'ordre des événements et la correspondance de scope/snapshot ; il ne juge pas automatiquement la pertinence de la justification. Choisir `create` reste légitime lorsque domaine, indépendance, licence ou intégration rendent la réutilisation inadaptée. Une ressource trouvée sur une branche non mergée n'est pas annoncée comme disponible localement.

Le vocabulaire canonique de discovery sépare identité et méthode. `decision` vaut `reuse` si l'identité logique cible est conservée, y compris pour une nouvelle version, ou `create` si une nouvelle identité est créée. `strategy` vaut `use_existing`, `coordinate`, `wait`, `copy`, `adapt` ou `new`. Couples autorisés : reuse avec use_existing/coordinate/wait/adapt ; create avec copy/adapt/new. `adapt` exige des `candidate_ids` et, pour reuse, un `target_resource_id` existant ; pour create, le nouvel ID cible est attribué à la création. `copy` implique create ; `new` peut être justifié malgré des candidats. Le reçu garde provenance, snapshot et justification dans tous les cas.

La provenance du reçu est discriminée invocation/replay/control_plane et les `source_refs` sont typées selon [F009](../specs/shared-knowledge.md). `validation_basis` fixe le contexte et les bornes vérifiés avant effet ; un `DiscoveryUseObservation` distinct prouve l'usage historique de ce reçu pour l'opération et la cible/version observées. La clôture réconcilie cette histoire avec la cible livrée. Une revalidation finale n'antidate jamais la recherche ; l'exception vise uniquement l'effet propre exact ou la publication identique prouvée. Une modification pertinente, une provenance absente ou une borne expirée exige revalidation/refus/unknown. Une création manuelle autorisée ne requiert aucun agent artificiel.

## Import, publication et suppression

L'import d'un répertoire Agent Skills commence comme donnée documentaire non fiable. Les scripts sont inertes jusqu'à classification explicite d'outil et autorisation. Le code interne Unleash reste Rust ; les repositories développés peuvent être Python, TypeScript, Java, Go, Rust ou multilangages, et leurs outils externes sont autorisables par les mêmes mécanismes. Le format tiers ne dicte ni le runtime interne ni les permissions.

Publier exige références résolues, validation structurelle et sémantique, rapport d'évaluations applicable, provenance et contrôle de permission. Un test de publication peut être purement déterministe. La révocation arrête les nouveaux bindings et peut bloquer les actions selon son motif. La suppression physique attend la politique de rétention des runs et preuves ; l'index dérivé n'est pas l'unique copie d'une version. Un run ancien doit rester reconstituable sans secret ni contenu supprimé illégalement ; lorsqu'un contenu est purgé, son tombstone et les limites de reconstitution deviennent visibles.
