# Workspace Rust et frontières natives

**Statut : découpage canonique retenu en R7 (ADR-03, ADR-15) ; ce dossier ne fournit aucun code produit.** Le code vit dans ce même dépôt, à la racine : workspace Cargo `crates/`, renderer `apps/gui-renderer/`, expériences `spikes/` et preuves `qualification/` ([démarrage M0](../dev/m0-kickoff.md)). Les versions de documentation observées figurent dans [la recherche systèmes](../research/systems-sources.md). Le produit reste V1 dans son ensemble ; les étapes de construction servent à maîtriser les dépendances, sans retirer les connecteurs, la GUI ou les capacités d'orchestration.

## Règle de langage

Le cœur applicatif et système développé pour Unleash est Rust : daemon, workers, process-host, autorité, orchestration, clients terminal, tests du cœur et utilitaires propres à ces composants. Les bibliothèques existantes, moteurs et outils ne sont pas réimplémentés pour leur imposer un langage. HTML/CSS et le renderer React/TypeScript d'[ADR-03](adr/ADR-03-rust-gui.md) sont autorisés pour la présentation. La [politique canonique R2 complétée R3–R5](../brief/implementation-policy.md) remplace la lecture absolue du brief initial. Python, TypeScript, Java, Go, Rust et dépôts multilangages sont supportés pour les projets supervisés via leurs outils externes, sous le même broker et les mêmes scopes. Un script d'automatisation utilisateur dans ces langages est un artefact de projet autorisé, distinct du code métier interne d'Unleash.

Les dépendances natives sont inventoriées et versionnées : SQLite C, libc et interfaces OS, moteurs graphiques, TLS et parseurs éventuels font partie de la nomenclature autorisée. La GUI retenue par [ADR-03](adr/ADR-03-rust-gui.md) comporte un hôte Tauri 2 Rust (`unleash-gui`) et un renderer React + TypeScript strict construit par Vite et embarqué dans le bundle, dans `apps/gui-renderer/` avec `pnpm-lock.yaml` ; Node.js et pnpm servent seulement au build. Les types TypeScript sont générés depuis les DTO Rust (ts-rs) et la CI échoue sur toute dérive. Ce renderer est une couche de présentation, pas une migration du métier. Le code généré et l’outillage existant sont recensés. Aucun assouplissement ne permet d’implémenter les états, permissions ou transitions dans un frontend.

Ce découpage fixe les responsabilités, sans obliger à créer une crate par ligne avant le premier test. Des modules peuvent démarrer dans un même crate tant que les directions restent vérifiables. `engine::automation` appartient au harness existant : pas de serveur d'automatisation avec sa propre DB ou son propre scheduler. Le workspace partage un `Cargo.lock` et des paramètres communs suivant le [modèle Cargo](https://doc.rust-lang.org/cargo/reference/workspaces.html). Le renderer vit dans `apps/gui-renderer/`, hors workspace Cargo ; son manifeste et `pnpm-lock.yaml` n'introduisent aucun second backend. Le domaine ne dépend jamais de l'adaptateur qui l'exécute.

Le [BrowserPort](browser-execution.md) du profil `mediated` repose en V1 sur l'adaptateur WebDriver W3C `fantoccini` piloté en Rust, sur Chrome for Testing et chromedriver du même build, épinglés par version et SHA-256 et préparés explicitement sous mandat (Q-18) ; Playwright MCP n'est pas un backend V1. Le profil `project_script` exécute un artefact Playwright/Selenium et son runtime/lockfile sous F011 ; le code reste externe, son niveau d'observabilité et de confinement est déclaré. L'absence de médiation instruction par instruction interdit de prétendre contrôler tous les effets métier du script.

Les trois serveurs d'inférence locaux sont des dépendances externes identifiées. Leur version/build, modèle/révision disponible, template, quantification et configuration appartiennent à la qualification ; un endpoint déjà géré par l'utilisateur constitue la voie initiale. Aucun téléchargement de poids, préchauffage ou lancement de serveur n'est un effet implicite de Settings. Un serveur explicitement géré par Unleash utilise la supervision F011, sans nouvelle autorité. Voir [local-models.md](../specs/local-models.md) et ses sources primaires.

## Choix de runtime et de stockage

Tokio est retenu pour les I/O asynchrones et les communications. Le writer SQLite vit sur un thread dédié à durée de vie explicite ; sa file bornée (8 demandes, ADR-01) refuse la surcharge par `ResourceBusy` avec le reason_code `BACKPRESSURE` avant d'accumuler sans limite. Des lectures à snapshot court peuvent utiliser des connexions distinctes. L'indexation, le calcul de hash volumineux et les outils projets ne s'exécutent pas dans une transaction ni sur un chemin qui bloque les heartbeats.

Les versions de Tokio et de `rusqlite` (features `bundled` et `backup`) sont figées par `Cargo.lock` (Tokio 1.54.1 et rusqlite 0.43.0 observées), sans ensemble compilé validé revendiqué ici. Le compilateur est figé par `rust-toolchain.toml` à 1.94.1 (R7), édition [Rust 2024](https://doc.rust-lang.org/edition-guide/rust-2024/index.html) ; le MSRV déclaré par `rust-version` du workspace est cette même version ([règles Rust](../rules/rust.md)). Une montée de toolchain est un changement isolé, avec CI verte.

Le mode SQLite embarqué est retenu (R7, ADR-01) pour maîtriser le correctif WAL-reset ; aucune SQLite système n'est admise en build de release. `SELECT sqlite_version(), sqlite_source_id()` et les options de compilation alimentent le manifeste de runtime. Au démarrage, `sqlite_source_id()` doit égaler la valeur compilée, sinon refus `InternalFailure/STORAGE_BUILD_UNQUALIFIED`. Voir [sqlite-design.md](sqlite-design.md).

## Frontières de sécurité et de livraison

`unsafe` est refusé au niveau du workspace (`unsafe_code = "deny"`) ; chaque crate hors adaptateurs ajoute `#![forbid(unsafe_code)]` à sa racine ; seuls les adaptateurs OS recensés `unleash-platform` et `unleash-process-host` le lèvent localement par `#[allow(unsafe_code)]` ciblé, avec contrat de validité `// SAFETY:` et tests OS ([règles Rust](../rules/rust.md)). Un `forbid` hérité du workspace ne pourrait pas être levé localement (erreur E0453). Aucun shell construit par interpolation n'est nécessaire pour les commandes ordinaires : le broker passe programme et arguments séparés. Le shell interactif est un type d'action explicite, observable, avec permissions et effets possibles plus larges.

Le worker reçoit une capacité étroite liée à son invocation, scope et fence. Les secrets fournisseur restent dans le daemon ou un composant autorisé, jamais dans le contexte du modèle, un argument de commande ou le journal. L'agent `SMAppService` du bundle signé Developer ID et notarisé (Q-16, [ADR-14](adr/ADR-14-local-data-oss.md)) s'installe sans root ; les [mécanismes Apple](https://developer.apple.com/documentation/servicemanagement/smappservice) imposent des règles de packaging et d'approbation OS, dont la préservation après mise à jour reste à démontrer (gate EXT-DIST).

## Vérification attendue

Le premier ensemble de preuves doit établir build reproductible macOS/Linux, inventaire réel des dépendances, respect de la frontière cœur Rust / présentation, fermeture des clients sans arrêt daemon et processus contrôlés après crash. Les tests sur des dépôts Python/TS/Java/Go/Rust/multilangages vérifient que la règle interne n'a pas rétréci le produit. Une procédure CSV sans Git et sans invocation agente, un replay zéro modèle et une supervision par blocs bornée complètent cette matrice. Les moteurs navigateur et serveurs locaux sont qualifiés avec leurs binaires/configurations réels, pas uniquement avec des mocks HTTP. GUI et TUI sont qualifiées sur packaging, accessibilité, usage CPU, diffusion des événements et [parité complète](../design/gui-tui-parity.md), y compris parcours guidé et configuration locale. Les commandes de test futures figurent dans [la stratégie de vérification](../testing/test-strategy.md) ; aucun résultat de compilation ou de runtime n'est revendiqué dans ce dossier.
