## Pièces requises pour AI-Guard

Fournir le dépôt et le commit de référence ; manifeste des services ; OpenAPI/proto/schémas réellement utilisés ; mécanisme d'authentification et de création d'identité agent ; modèle de permissions et décisions ; règles de fail-open/fail-closed ; schémas d'audit et de corrélation ; support d'idempotence ; timeouts/retries ; gestion de révocation et décisions en vol ; garanties d'isolation par OS ; déploiement minimal et compatibilités ; tests contractuels et scénarios d'incident. Les noms de fichiers éventuels doivent venir du dépôt, pas être inventés.

Sans ces pièces, le dossier spécifie le côté Unleash (ADR-10 accepté) mais ne peut confirmer que l'AI-Guard existant le remplit. C'est la gate de recette externe EXT-GUARD, pas un retrait de fonctionnalité V1 ni une décision en attente.

## Réalisation dans ce dépôt

Depuis R7, le code d'Unleash est développé dans ce dépôt, à côté du dossier : workspace Cargo à la racine (`crates/`), renderer GUI (`apps/gui-renderer/`), expériences M0 (`spikes/`) et preuves réelles (`qualification/`). Le point d'entrée des agents est `AGENTS.md` et le démarrage de M0 est décrit dans [m0-kickoff](../dev/m0-kickoff.md). Les interfaces communes sont figées en M0 avant le développement parallèle des dépendances.

## Q-21 — Déclenchement calendaire de nouveaux Runs

**Statut : résolue R7, écartée de la V1.** R3 confirme le rejeu avec d'autres données, notamment en relançant le script le lendemain ; elle ne demande pas une planification autonome. La V1 ne crée donc ni objet RunSchedule, ni timer calendaire de création de Run, ni opération, groupe de parité ou réglage de planification. Elle conserve intégralement la réutilisation explicite d'une version publiée avec une nouvelle AutomationDataRevision par les opérations de Run existantes, les timers internes et échéances des workflows, les files et le scheduler de ressources. La CLI non interactive reste scriptable : un ordonnanceur externe choisi par l'utilisateur (launchd, systemd, cron) peut l'appeler comme n'importe quel programme, sous les mêmes mandats et budgets. Une demande ultérieure de planification intégrée ferait l'objet d'un nouvel ADR, avec contrat typé (fuseau et version des règles, échéance manquée, absence de chevauchement, budgets cumulés), opérations communes, parité et tests DST/crash/idempotence.
