# Acceptation F019

**Critères proposés, non exécutés.** Chaque ligne correspond à l'exigence, au test et à la preuve de même suffixe. Les fixtures sont synthétiques ; aucun achat, paiement ou écriture comptable réelle n'est nécessaire pour démontrer ces critères.

| ID | Given / When / Then |
|---|---|
| AC-F019-001 | Étant donné une version offrant replay et supervision par lots, quand les deux modes sont sélectionnés dans deux runs, alors replay impose forbidden et zéro tâche agente, tandis que supervised n'admet ses leader_decision qu'aux checkpoints/exceptions déclarés dans la fréquence et le budget prévus ; le nombre de clics ne provoque pas autant d'appels LLM. |
| AC-F019-002 | Étant donné une trace apparemment réussie et un candidat qui contredit le résultat métier de référence, quand la publication est demandée, alors discovery, provenance et contradiction restent inspectables et les gates applicables refusent la publication ; le claim du générateur ne remplace pas l'oracle. |
| AC-F019-003 | Étant donné une procédure avec opérations connues et bornées, quand elle est compilée, alors elle utilise le WorkflowReducer et le profil épinglé v1.1 ou v1.2 ; for_each exige v1.2 ; une opération inconnue, une expression libre, une borne dépassée ou une tâche agente cachée sous forbidden est refusée avant effet. |
| AC-F019-004 | Étant donné un run épinglé puis une publication v2, un alias déplacé et un driver mis à jour, quand le run continue ou reprend, alors ses références exactes restent celles engagées ; une dépendance v1 indisponible bloque sans substitution. |
| AC-F019-005 | Étant donné un CSV valide puis des variantes avec erreur tardive, ambiguïté de locale, doublon de clé et cellule ressemblant à une formule, quand l'import/validation est effectué, alors les valeurs sont traitées selon le profil publié, les erreurs précèdent tout effet et aucune cellule n'est exécutée ; l'édition du fichier source crée une nouvelle révision. |
| AC-F019-006 | Étant donné un replay complet avec providers piégés, modèle local instrumenté et descendants surveillés, quand il exécute ses actions, checkpoints, reprise et rapport et que des chemins indirects tentent un appel modèle, alors aucun dispatch n'atteint un modèle ; les tentatives sont refusées et l'ensemble des composants contrôlés est couvert par la preuve. |
| AC-F019-007 | Étant donné trois invocations agentes et deux workers d'action admis sous limite globale cinq, quand un sixième travail arrive, alors il attend ; les compteurs distinguent les cinq unités et aucun pool de replay parallèle n'étend le plafond, y compris aux checkpoints, reprises et changements de limites. |
| AC-F019-008 | Étant donné une procédure apprise avec un scope plus large que le mandat actuel ou une permission révoquée avant dispatch, quand son action est demandée, alors l'intersection actuelle refuse l'effet et aucun secret ni droit de l'apprentissage n'est réutilisé comme grant. |
| AC-F019-009 | Étant donné une cible reclassée dans le DOM, une cible en double et un bouton CSS encore valide associé au mauvais article, quand la résolution a lieu, alors seul le cas à identité unique conforme peut continuer ; ambiguïté/dérive bloque sans prendre arbitrairement le premier élément. |
| AC-F019-010 | Étant donné un clic accepté ou un script exit 0 mais une quantité, un compte, une devise ou un total incorrect, quand les postconditions et done sont évalués, alors le run n'est pas réussi ; l'effet incorrect connu est distingué de l'effet inconnu et une décision LLM ne peut effacer l'assertion en échec. |
| AC-F019-011 | Étant donné un effet accompli dont le receipt est perdu, quand crash/retry/réparation ou nouveau CSV surviennent, alors l'effet reste outcome_unknown et aucune répétition automatique n'a lieu ; seule la réconciliation ou disposition autorisée explicite permet une suite dont la provenance est conservée. |
| AC-F019-012 | Étant donné un checkpoint avec plusieurs lignes traitées puis la perte du worker et du navigateur, quand la reprise est autorisée, alors elle retrouve données/cursor/effets/budgets depuis l'état durable, réobserve la cible sous nouveau fence et ne prétend restaurer aucun handle DOM ou état RAM. |
| AC-F019-013 | Étant donné un run bloqué par dérive, quand une réparation est demandée ou déclenchée par une politique préautorisée valide, alors un job et un draft distincts sont créés, la publication produit v2 et le run v1 reste inchangé ; sans mandat de réparation, aucune invocation de conception ne démarre. |
| AC-F019-014 | Étant donné un script de projet et son runtime verrouillés, quand il est qualifié pour replay, alors son profil indique l'observabilité réelle et démontre les contrôles modèle/réseau/processus requis ; leur absence produit IsolationUnavailable et jamais une attestation zéro modèle trompeuse. |
| AC-F019-015 | Étant donné un run partiel avec lignes réussies, assertion fausse, effet inconnu et coûts de supervision éventuels, quand son rapport est produit/reproduit au même watermark, alors il restitue les mêmes faits et limites par template, relie les preuves et n'appelle aucun rédacteur LLM supplémentaire. |
| AC-F019-016 | Étant donné les mêmes versions, données et autorités, quand GUI, TUI et CLI effectuent les parcours F019 et se reconnectent après perte d'un reçu, alors elles utilisent les mêmes opérations/états/erreurs et ne créent aucun run ou effet dupliqué. |
| AC-F019-017 | Étant donné une authentification expirée ou un challenge humain, quand le driver ne peut poursuivre, alors le run attend durablement sans modèle de secours, conserve les réservations nécessaires et ne reprend qu'après nouvelle observation d'identité/mandat/préconditions. |
| AC-F019-018 | Étant donné une version dépréciée, révoquée ou dont un objet a été purgé, quand elle est sélectionnée ou reprise, alors le registre et le broker appliquent leur politique exacte, signalent les objets manquants et n'adoptent jamais silencieusement une autre version. |

La campagne vérifie séparément zero-model replay et supervision bornée. Une réparation LLM autorisée dans un job distinct ne dégrade pas rétroactivement le compteur du replay, mais doit apparaître dans le total et le rapport de la mission. Une preuve limitée à un mock ou à un OS est qualifiée comme telle.
