# F012 — interfaces et contrats

## Contrats proposés

ModelSelectionRequest : project_id, repository_id éventuel, role_binding, primary_skill_binding exact, overrides, required_capabilities, data_policy_ref et model_policy_ref lorsqu’un run porte cette politique. Le resolver charge les ModelSelectionBinding autorisés depuis le snapshot de configuration ; un client ne peut injecter leur priorité. ResolvedModelProfile : provider/model/dialecte, profile_version/digest, selection_binding_refs exactes, champ→source de priorité, contraintes, fallback_candidates, capability_evidence_ref et inference_placement_evidence_ref. Les modèles locaux suivent la même priorité que les fournisseurs cloud.

ModelRequest : champs définis par la [spécification canonique](../../specs/model-routing.md#contrats-internes-proposés) — origin_ref typé, action_id, model_call_id, provider_profile_version, model_id, capability_requirements, context_ref typé, generation_limits, output_contract_ref, tool_catalog_digest, budget_reservation_id, deadline et références des politiques modèle/données effectives. ProviderStream retourne des événements normalisés ; ModelOutcome termine l’appel avec status, output_refs, usage et provider_request_id éventuel. L’interface de transport reçoit une SecretRef seulement lorsque le profil exige un secret ; elle ne sérialise jamais le secret dans l’enveloppe IPC publique.

## Sélection et compatibilité

Les valeurs d’effort et limites restent propres au profil modèle vérifié. Une option inconnue est refusée ou portée en extension fournisseur explicitement autorisée, jamais silencieusement ignorée. Le fournisseur compatible déclare son dialecte ; son endpoint est une configuration privilégiée.

La politique de coût comporte currency, pricing_version, pricing_source, reservation_upper_bound, unknown_cost_hold, `cost_bound_mode` (`strict` par défaut, Q-07 : un coût maximal non bornable est refusé) et `pricing_stale_policy` (`block`|`warn`, défaut `block`, Q-14). Les valeurs initiales R7 (comptes, alertes, retries, fallback) sont dans [model-routing](../../specs/model-routing.md). Le débit est contrôlé par fournisseur/compte/modèle et le plafond de slots par F003 : une seule limitation ne remplace pas les autres.

## ModelSelectionBinding versionné — R6

Ce DTO de configuration appartient à F012 ; il ne change pas `skill.schema` ni la publication F007. Sa forme normative est : `binding_id`, `binding_version` entier positif, `configuration_scope`, `skill_ref`, `preferred_profile_ref`, `state=active|removed`, `command_receipt_id`, `principal_id` dérivé du transport et `digest`. `configuration_scope={kind:global|project|repository,owner_id}` impose owner_id nul pour global et l'identité exacte pour les autres. `skill_ref={skill_id,skill_version,skill_scope:{kind,owner_id}}` désigne une version publiée dans son namespace exact ; Pour state=active, `preferred_profile_ref={profile_id,profile_version,digest}` pointe un profil immuable ; pour state=removed, cette référence est nulle et l'ancienne version demeure inspectable. Le profil contient fournisseur/modèle/dialecte et paramètres natifs qualifiés ; le binding n'embarque ni secret ni grants.

`SetSettings` accepte le patch typé `model_selection_binding` avec `operation=upsert|remove`, `configuration_scope`, `skill_ref` et, pour upsert, `preferred_profile_ref`. `expected_revision` contrôle l'agrégat Settings du scope. Le backend vérifie ses droits d'édition, les références exactes et l'absence d'expansion d'autorité, attribue l'identité stable de la clé et sa version monotone, calcule le digest canonique et renvoie binding_ref/révision/receipt. Supprimer crée une version `removed` sans effacer l'historique ; mettre à jour crée une nouvelle version. La clé unique active est `(configuration_scope, skill_ref)` ; principal/receipt ne viennent pas de valeurs déclarées libres.

Résolution dans une transaction de snapshot de configuration : dériver le skill principal de `role.entry_skill`, chercher à ce niveau repository > projet > global parmi les scopes applicables, puis appliquer la priorité canonique entre niveaux. `removed` signifie absence dans ce scope et autorise la recherche au suivant ; une référence active invalide produit `ModelConfigurationConflict`. Aucun élargissement par homonyme, version voisine ou autre skill n'est permis. `preferred_profile_ref` choisit atomiquement provider/modèle/dialecte ; les options surchargées sont validées sous cette identité. Les références de binding et de profil gagnantes, ainsi que les sources des paramètres retenus, sont épinglées dans InvocationBundle avant admission. Une modification ultérieure n'affecte ni une invocation matérialisée, même en file, ni sa reprise ; elle est candidate pour une prochaine matérialisation autorisée par le run.

Un provider_probe utilise directement son profil exact autorisé et ne résout pas de préférence de skill : il n'a ni rôle ni skill fictif.

## Événements et erreurs

ModelCallPrepared → ModelCallDispatched → ModelCallCompleted/ModelCallInterrupted/ModelCallFailed, puis UsageReconciled si nécessaire. ModelFallbackSelected porte la cause, les anciens/nouveaux profils et l’autorité qui l’autorise. Les sorties d’outils deviennent ToolActionProposed, jamais actions exécutées dans l’adaptateur.

Les reçus IPC suivent le pipeline [IPC v2](../../architecture/ipc-and-apis.md) : authority_generation est vérifiée avant toute recherche de reçu ; dans la lignée active, la même clé acteur/command_id et le même digest de commande (lignée incluse) retournent le reçu conservé, sans recontrôle de expected_revision. Une requête modèle déjà dispatchée ne doit pas être recréée à partir d’un simple refresh GUI.

Le transport commun et les codes d’erreur sont définis dans [ipc-and-apis](../../architecture/ipc-and-apis.md). Les noms de DTO ci-dessus sont des propositions Unleash, pas des APIs de bibliothèques ou services supposées existantes.


## Identité et immutabilité d'un appel

ModelCallManifest porte model_call_id, action_id, origin_ref, provider_profile_ref, model_id, capability_snapshot_ref, context_ref, tool_catalog_digest, output_contract_ref, budget_reservation_id et parent_model_call_id éventuel. Il est engagé avant dispatch et immuable. Le retry technique d'une même action reste une tentative de transport historisée (action_dispatches.ordinal), sous le même model_call_id et le même manifeste ; un fallback vers un autre profil constitue une nouvelle action et un nouveau manifeste, liés à la cause. Le bundle initial ne change pas.

Le primary_skill_binding de ModelSelectionRequest est dérivé de role.entry_skill de la liaison effective de tâche, et non d'un choix indépendant non tracé. Les skills auxiliaires ajoutent des besoins de capacités sans devenir des priorités concurrentes.

ModelCallRecord porte l'évolution de transmission prepared/dispatch_attempted/completed/unknown/not_sent et références d'observations. Le manifeste conserve exactement le payload préparé et ses exclusions ; l'interface affiche séparément ce qui a été remis au transport et ce dont la réception fournisseur est confirmée. Une déconnexion après envoi ne prouve pas une absence de réception.

## Contexte v2, filiation et stockage — R6

`ContextManifest` version `unleash.context.v2` conserve ses identités d'invocation et ajoute `context_mode=explicit_unleash_history`. Chaque segment porte `effective_data_policy_ref` et `lineage={kind:source|derived,status:complete|unknown,source_refs,producer_action_ref}`. Une référence de politique est `{id,version,digest}` ; chaque entrée de source référence identité/révision/hash et la politique exacte. Une source directe a une liste d'antécédents vide et aucun producteur ; un dérivé complet a au moins un antécédent et une action productrice. L'inclusion exige filiation complète, politique connue, hash connu et octets disponibles, y compris chiffrés si opaques. Les références manquantes restent représentables dans un segment exclu avec raison.

`ContextDataPolicy` porte ACL, localité, destinations et obligations de conservation par catégorie de copie. Le validateur de domaine vérifie existence/digests, fermeture acyclique des sources, intersection conservatrice et autorité avant dispatch. `declassification_ref` référence, lorsqu'elle existe, la décision immuable décrite dans [model-routing](../../specs/model-routing.md). Le schéma valide la forme ; il ne démontre ni l'autorité ni la conformité d'une politique. Une filiation complète n'exige pas de ressusciter des octets purgés, mais exige les métadonnées encore légitimement disponibles pour contrôler les dérivés et les suppressions héritées.

`RecordDeclassificationDecision` est la seule commande qui enregistre une décision de déclassification ([catalogue client](../../architecture/client-operation-catalog.md), owner F012, parité PAR-SETTINGS-03). Son payload porte sources et politiques exactes avant/après, transformation, destination, digest du contenu visé, portée, validité et justification. Le principal est dérivé du transport : seul un humain autorisé sur chaque source et sur la destination peut l'engager, jamais un modèle, un agent ni une redaction. La décision est immuable et liée à son receipt ; une décision expirée, hors portée ou visant un autre digest n'autorise aucune inclusion. Refus : `CapabilityDenied/DECLASSIFICATION_AUTHORITY_REQUIRED` (after_human_decision) lorsque l'autorité manque, `ContractViolation/DATA_POLICY_CONFLICT` (after_human_decision) lorsque les politiques sont inconciliables ; le nom de domaine du premier est DeclassificationAuthorityRequired.

Un segment `provider_opaque` porte aussi `opaque_metadata` : provider_profile_ref, dialect_ref, origin_model_call_id, content_ref, protocol_purpose, protocol_qualification_ref et dependency_manifest_refs (ID/digest exacts). Ces métadonnées qualifient des octets explicitement inclus, jamais une référence à un historique caché. Un producteur/antécédent hors politique empêche la réutilisation du bloc. Ses octets ne sont pas exposés comme raisonnement lisible et ne sont pas traduits pour un autre fournisseur.

Le sérialiseur V1 refuse `previous_response_id`, `conversation` et tout équivalent de continuation serveur, y compris dans une extension native. Les IDs de réponse restent permis comme observations de corrélation. La qualification du dialecte porte aussi sur absence d'historique implicite, paramètres effectifs de stockage fournisseur et conservation applicable ; le mode explicite n'est pas une preuve de rétention nulle. Les raisons IPC supplémentaires sont `CapabilityDenied/REMOTE_CONTEXT_REFERENCE_FORBIDDEN`, `ContractViolation/CONTEXT_LINEAGE_INCOMPLETE` et `ContractViolation/DATA_POLICY_CONFLICT` ; les noms de domaine correspondants sont RemoteContextReferenceForbidden, ContextLineageIncomplete et DataPolicyConflict. Elles ne sont pas réessayables automatiquement avant correction des préconditions. Les anciens manifests v1 sont des archives ; aucune valeur de filiation ne leur est inventée pour les convertir en appels v2.

## Profils et observations des modèles locaux

Ces extensions sont des DTO Unleash proposés, pas des champs universels des API externes.

| ProviderProfile | provider_kind dont `lmstudio`, `ollama`, `llama_cpp` ; dialecte/version ; endpoint normalisé ; auth_mode ; SecretRef éventuelle ; politique de transport ; propriétaire du serveur et mode de gestion ; tarif appliqué `pricing_version`, `price_valid_until`, `source_kind` et `pricing_stale_policy` (Q-14) ; un profil local déclare `pricing=none_local` et reste borné par tokens, temps et ressources ; état `blocked` avec motif tant que `TestProviderProfile` n'a pas réussi ou que le modèle est absent de l'inventaire du compte (Q-07). |

| CapabilitySnapshot | Backend/build, modèle, digest/template/quantification disponibles, contexte effectif, capacités déclarées/testées/inconnues, preuves, date et invalidations. Un alias ne garantit pas l’identité des poids. |
| InferencePlacementEvidence | Machine/placement et relais autorisés connus, méthode de vérification, configuration/processus observés, date, limites et état vérifié/inconnu. `local_only` refuse un état inconnu. |

`SetProviderProfile` et `TestProviderProfile` restent les commandes communes du [catalogue](../../architecture/client-operation-catalog.md). Le test distingue validation, connexion, inventaire et probe de génération avec leurs effets et limites ; il n’est pas déclenché par un simple rafraîchissement d’écran. Les mêmes payloads révisionnés sont utilisables depuis GUI, TUI et CLI. Une politique `forbidden` liée au run est vérifiée avant probe, chargement, démarrage de processus ou inférence pour ce run.

`SetProviderProfile` vise l’agrégat du profil par `aggregate_id`. Cet UUID est l’identité stable du profil et sa représentation canonique est utilisée par `profile_id` dans `TestProviderProfile`. `expected_revision=0` crée la première version. Pour une révision, le writer compare `expected_revision` à la version courante et attribue la version suivante. Chaque version est immuable et liée au reçu de configuration, à l’acteur authentifié et à la portée autorisée. Le rejeu suit le [contrat d’idempotence IPC v2](../../architecture/ipc-and-apis.md). Un reçu encore disponible est restitué pour la même lignée active, le même acteur, le même `command_id` et le même digest de requête.

La version fige la configuration exacte et son digest RFC 8785 et SHA-256. Elle associe le fournisseur, le dialecte, l’endpoint, le modèle, les paramètres autorisés, les bornes, la localité, le tarif applicable et la référence de secret éventuelle. Le serveur contrôle le tarif dans le catalogue ou la déclaration autorisée. Il n’accorde aucune capacité ou preuve de placement sur la seule déclaration du client. Le serveur valide l’identité canonique lors de la résolution de `(profile_id, profile_version)` pour la lecture et pour le probe. Les observations de qualification référencent cette version sans avancer la révision de configuration. Une configuration modifiée requiert sa propre qualification avant activation. La configuration ne déclenche aucun probe ni résolution de secret.

### Payload de configuration IPC v2

Le [schéma de commande](../../schemas/ipc-command.schema.json) ferme le payload de `SetProviderProfile`. Il porte `provider_kind`, `dialect` (`kind`, `version`), `endpoint`, `model`, `locality`, `server_management`, `auth`, `limits`, `declared_capabilities` et `pricing`. Chaque fournisseur déclare un des dialectes compatibles énumérés par le schéma. La version du dialecte et les six limites sont des entiers positifs jusqu’à 9 007 199 254 740 991. La liste comporte au plus 64 capacités distinctes. Les références et capacités utilisent des chaînes non blanches sans caractères de contrôle, avec une limite de 256 octets UTF-8 au décodage.

`auth` porte `none` ou `secret_ref` avec la référence opaque. Le serveur doit vérifier la référence dans l’autorité F017. Les fournisseurs OpenAI et Anthropic natifs exigent une référence et un tarif. Le décodeur vérifie les URLs ASCII sans identifiants, requête ou fragment, dans la limite de 2 048 octets. Il restreint HTTP à un hôte loopback syntaxique. Le serveur normalise l’endpoint et qualifie le placement et l’accès séparément.

`pricing` distingue `none_local`, `catalog`, `user_import` et `user_declared`. La référence `catalog` porte identifiant, version et empreinte du catalogue, empreinte de l’entrée exacte et politique de péremption `block` ou `warn`. Elle préserve les paliers portés par l’entrée. Les variantes inline exigent les quatre taux, leurs dates, la devise et la provenance nullable. Les taux inconnus portent `null`. Les dates et taux sont des entiers non signés dans le domaine exact JSON, avec le constat antérieur ou égal à la fin de validité. Les entrées inline avec paliers sont refusées par ce format. Le service applique le catalogue et les règles Q-14 au tarif effectif.

La configuration peut référencer un modèle local à tous les scopes de sélection prévus. Les paramètres spécifiques restent dans une extension de dialecte validée ; aucun paramètre d’un backend n’est transmis arbitrairement à un autre. Chaque fallback produit le manifeste distinct déjà exigé ci-dessus et revalide destination, localité, capacités et réservations.

### Versions de configuration dans le Store

Le port V011 reçoit du service authentifié l’objet canonique de configuration et l’identité de son contenu publié. Le service contrôle la normalisation de l’endpoint et la provenance du tarif. Pour un catalogue, le Store recoupe l’identité, le digest des octets publiés, le pointeur vers l’entrée, son empreinte et les dates de publication et de validité fournies. Les paliers restent dans l’objet du catalogue. Une version configurée attend une qualification pour servir une requête de production. Enregistrer cette version ne déclenche aucun accès au fournisseur.

Lorsqu’une référence de secret est requise, le binding F017 porte `namespace=provider`, `purpose=api_key`, `target_kind=provider_profile` et l’UUID canonique comme `target_id`. La portée utilise `project` et son UUID ou `user/default` selon la configuration autorisée. Le writer recoupe la référence active, la portée, la cible, le type, le backend et leur révision. Il fige ces métadonnées avec la version. Le probe recoupe le binding à son tour avant effet. La valeur du secret reste dans son coffre.

Une demande de probe de profil configuré doit résoudre le couple exact UUID/version. Le writer relit aussi la référence technique, le modèle, la portée et le binding associés. La durée demandée reste dans la limite de génération épinglée par la version. Une demande pour un UUID configuré ne peut utiliser une référence historique comme substitut. Les versions d’origine et les références historiques restent lisibles sous leurs identités respectives. Voir le [contrat SQLite](../../architecture/sqlite-design.md#catalogue-de-modèles-r7).

## ProviderProbeContext sans agent — R6

TestProviderProfile possède les phases fermées `validate_config`, `connect`, `inventory`, `generation_probe`. Les trois premières ne génèrent pas de texte et ne préchauffent/chargent pas de modèle pour compléter silencieusement une donnée absente. Un endpoint dont l’inventaire charge implicitement un modèle ne peut être présenté comme inventaire passif ; le profil l’annonce et requiert le mandat correspondant. generation_probe teste le profil exact, sans fallback automatique.

Le [schéma IPC v2](../../schemas/ipc-command.schema.json) ferme le payload de `TestProviderProfile`. Les champs requis sont `profile_id`, `profile_version`, `phase`, `capability_set`, `limits`, `locality` et `mandate_ref`. La version est un entier strictement positif. Les références et les capacités sont des chaînes non blanches sans caractères de contrôle, limitées chacune à 256 octets UTF-8 au décodage. La liste conserve l’ordre demandé, comporte au plus 64 capacités et refuse les répétitions. `locality` est `local_only` ou `approved_remote`.

`limits` contient `timeout_ms` strictement positif, `max_calls`, `max_output_tokens` et `max_cost_usd_micros`, tous des entiers non signés. Ces quatre valeurs et `profile_version` sont bornées à 9 007 199 254 740 991 pour conserver leur valeur exacte entre clients. `generation_probe` demande de 1 à 3 appels et de 1 à 512 tokens de sortie cumulés, avec au plus 60 000 ms et 100 000 millionièmes de dollar. Les limites demandées sont ensuite bornées par les politiques effectives. Les phases passives gardent leurs propres règles d’effets et admettent zéro appel de génération, token ou coût.

Le serveur dérive l’acteur et la cause de la connexion authentifiée et de `CommandReceipt`, et résout le mandat, la localité réelle et les capacités dans leurs autorités. Une demande issue d’un run garde sa lignée et refuse `model_policy=forbidden`. Une commande de configuration indépendante et autorisée peut ouvrir un probe indépendant. Le probe transmet uniquement les données synthétiques de ses fixtures versionnées. Les éventuelles propositions d’outil satisfont le contrat de doubles locaux sans effet métier.

Pour `validate_config` au plan de contrôle indépendant, `mandate_ref` est l’UUID canonique du reçu de configuration engagé pour la version exacte du profil dans la lignée active. Le writer vérifie ce lien et conserve la provenance du configurateur. Il contrôle séparément l’acteur et le principal actuels, l’autorisation administrative, la portée et son gel. La référence causale ne confère pas de droit à son porteur. Un reçu historique reste inspectable mais ne permet pas une nouvelle validation sous cette règle. `connect`, `inventory` et `generation_probe` exigent chacun leur mandat d’effet et ne reconnaissent pas cette référence comme autorisation.

Pour les phases d’effet, `mandate_ref` désigne l’émission active du [mandat F017](../F017-ai-guard-integration/interfaces.md#mandats-de-sonde-fournisseur). Le writer contrôle l’origine, la portée et sa révision, le profil exact, la phase, la localité, les capacités et chacun des plafonds. Une référence inconnue, cachée, inactive ou incompatible rend `NotFoundOrHidden` avant préparation d’une nouvelle intention. Une lignée de commande périmée est refusée par l’enveloppe avant cette résolution. L’autorisation de joindre une destination n’atteste en elle-même ni le placement du modèle ni ses capacités.

`connect` et `inventory` enregistrent un contexte de transport propre à la phase et le lient à leur reçu, à la décision du broker et à la réservation de type probe du pool commun. Ils utilisent `network_egress`, dans les limites du profil, du mandat, et des plafonds du pool et du fournisseur. Ils ne créent aucun ModelCall ou ModelCallManifest. `connect` qualifie la connexion jusqu’au transport réellement observé. `inventory` qualifie uniquement l’échange d’inventaire permis. La référence de secret éventuelle est recoupée selon le profil. La valeur du secret reste réservée au transport autorisé pour l’échange qui en a besoin.

Pour un `connect` local sans identité de serveur qualifiée, l’admission est conservatrice. Les probes de connexion qui pourraient viser le même serveur partagent au plus une place, quelles que soient les références de profil. Une réservation détenue ou en réconciliation compte toujours. Une autre admission susceptible de viser ce serveur attend tant que ce chevauchement reste indéterminé. Une adresse loopback et un profil déclaré ne qualifient ni la séparation de deux serveurs ni le placement de l’inférence. Le plafond par serveur et les preuves de placement requis pour la qualification des modèles locaux restent applicables.

Le résultat positif de `connect` exige la preuve du transport fermé, attribuée à son dispatch et à sa requête. La publication de cette observation ne libère pas à elle seule la réservation. La phase de fin engage le résultat et la disposition selon le [contrat SQLite](../../architecture/sqlite-design.md#mandats-et-contexte-de-transport-fournisseur). À la perte d’un acquittement, la lecture du reçu et la réconciliation reprennent les faits engagés sans ouvrir une nouvelle connexion.

Le résultat de `validate_config` atteste uniquement les contrôles locaux réellement effectués sur la configuration de cette version, ses octets et ses liaisons. Il distingue les phases non testées et ne qualifie ni disponibilité du fournisseur ou du coffre, ni placement, valeur de capacité ou activation du profil. Il n’ouvre aucun socket, ne charge aucun modèle et ne réserve ni unité du pool global ni budget. Dans la lignée active, le même acteur, le même `command_id` et le même digest rendent le reçu déjà engagé avec sa référence de résultat si la réponse est encore conservée. Après purge de la réponse, le tombstone rend `ContractViolation/IDEMPOTENCY_WINDOW_EXPIRED` et la référence d’inspection selon le [contrat IPC](../../architecture/ipc-and-apis.md), sans produire une nouvelle observation. Une vue autorisée du profil peut lire l’observation disponible pour sa version exacte.

`GetProviderProfile` prend uniquement `profile_id` (UUID non nul) et `profile_version` (entier entre 1 et 9 007 199 254 740 991). La portée de l’enveloppe doit correspondre à celle de la version et être autorisée. Une version introuvable ou masquée rend `NotFoundOrHidden`. Le résultat porte l’UUID, la version, `profile_version_ref`, `configuration_digest`, `configuration_receipt_id`, `qualification` et `observations`, avec le watermark de la projection SQLite. Chaque élément d’`observations` contient la phase, le probe, la référence du résultat, l’instant et le statut observé.

La lecture rend la dernière observation de validation locale de cette version tant que sa preuve est conservée et vérifiable. La purge de sa notification ne la retire pas à elle seule. Une preuve manquante ou illisible pour le résultat le plus récent rend `ContractViolation/EVIDENCE_UNAVAILABLE`, même si une preuve plus ancienne est encore conservée.

Avant génération, persister `ProviderProbeContext` : probe_id, command_receipt_id, principal_id, scope, source_run_id éventuel, profile exact, fixture/digest, payload_manifest_hash, politiques/digests, bornes et réservations, `context_mode=explicit_unleash_history` et filiation/politique des seuls éléments synthétiques de fixture. Il ne contient ni agent_id ni session agente fictive. `ModelOrigin` est une union fermée : invocation `{invocation_id,attempt_id,invocation_bundle_digest}` ou provider_probe `{provider_probe_id,probe_context_digest}`. `ModelContextRef` est invocation_context ou provider_probe_context. Le ModelCallManifest immuable référence ces unions et le payload exact ; ModelCallRecord conserve les observations de transmission et d’usage habituelles.

Le probe actif est une troisième classe d’unité dans le **même** pool global 5/50, soumise aussi au max_inflight fournisseur et aux budgets. La file est persistante, avec une tentative/fence active unique. Une annulation/timeout n’efface pas une génération potentiellement active : capacité locale et réserve financière sont libérées seulement selon les preuves et règles communes. Un calcul distant devenu inaccessible reste inconnu, pas déclaré arrêté par fermeture de socket. Aucun pool parallèle de tests n’existe.

Bornes V1 du profil de fixture (confirmées par Q-07) : au plus 3 appels, 512 tokens de sortie cumulés, deadline 60 secondes, coût explicite réservé d'au plus 0,10 USD par probe cloud (Q-07) ou coût fournisseur local qualifié nul ; toutes sont encore réduites par les politiques utilisateur. Une erreur de capacité produit un résultat de qualification, jamais une nouvelle équipe d’agents. Le résultat distingue configuration/connexion/inventaire/génération réellement testés et déclaré/non testé/inconnu.
