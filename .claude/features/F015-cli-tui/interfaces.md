# F015 — interfaces

Statut : grammaire de conception proposée, aucun exécutable ni endpoint nouveau livré. Les commandes ci-dessous sont des entrées utilisateur vers les façades communes, pas une deuxième API métier. La [matrice GUI/TUI/CLI](../../design/gui-tui-parity.md) précise les parcours et leurs preuves.

## Entrées et catalogue

unleash tui ouvre l’application interactive complète. Les autres commandes restent utilisables sans TTY. L’aide et les complétions décrivent chaque opération, ses arguments, sorties, permissions et codes. Les sélecteurs project/profile, command_id, expected_revision, format et wait/timeout sont communs quand applicables. Une mutation scriptée persiste d’abord son intention locale {command_id, authority_generation, digest, enveloppe canonique} avant le premier envoi ([IPC](../../architecture/ipc-and-apis.md)).

Ces familles sont des grammaires proposées vers les noms wire de [l’IPC](../../architecture/ipc-and-apis.md) et les payloads propriétaires. Une vue d’édition ne crée aucun moteur ou contrat parallèle. Le [catalogue commun](../../architecture/client-operation-catalog.md) fixe tous les noms, notamment **11 commandes/5 lectures propres F019 et 4 commandes/4 lectures GuidedSetup**. Chaque mapping doit être qualifié pour les trois clients ; il ne peut devenir une mutation directe ou un endpoint privé TUI. La matrice conserve 58 groupes dans dix espaces.

Les mises à jour signées de l’application et du paquet CLI/TUI ne sont pas des opérations du daemon : l’updater de distribution les applique sur commande de l’utilisateur, hors protocole IPC ([ADR-14](../../architecture/adr/ADR-14-local-data-oss.md), amendement R7). Cette grammaire ne leur raccorde aucune opération du catalogue.

Les mutations d’objets existants transmettent expected_revision ; les créations respectent la convention du protocole. Opérations longues : operation_id, state et event_cursor. Les commandes de composition acceptent un document versionné ; l’entrée n’est jamais évaluée comme du shell. Un parseur doit traiter les valeurs littéralement et diagnostiquer les champs invalides.

## Payloads guidés, modes et fournisseurs

setup draft create/save accepte un document structuré de template/version/digest, goal, sources, paramètres, mode, budgets et permissions ; provider est requis uniquement si les étapes déclarées utilisent un modèle. setup preview restitue une projection déterministe et ses inconnues ; setup apply transmet révision/digest et validation/aperçu applicables. Le reçu décrit les agrégats locaux créés/réutilisés, dont rôles/agents seulement si nécessaires. Un template peut être personnalisé sans compétence préalable en workflow. Aucun juge LLM, probe ou StartRun n’est ajouté par la CLI.

run create pour une automation porte référence exacte, AutomationDataRevision, automation_mode et paramètres. replay exige forbidden ; supervised exige workflow/bindings de supervision publiés et allowed_bounded. GetRun expose blocs, checkpoints/exceptions prévus, ObservationReport, assertions, références de logs, décisions, appels et effets. Les opérations StartRun/PauseRun/ResumeRun/CancelRun restent les mêmes. Une commande nouvelle ne contourne pas la réconciliation d’un effet antérieur inconnu.

provider set transporte profil/dialecte lmstudio/ollama/llama_cpp ou compatible, endpoint, auth_mode, SecretRef si requise, localité/capacités/ressources/fallback. provider test porte phase et bornes ; charger ou générer doit être explicite. provider list/show et doctor lisent l’état observé et sa fraîcheur sans boucle de tests cachée. local_only ne permet pas un fallback cloud et forbidden interdit même un appel local ; les deux axes sont distincts. Voir [local-models](../../specs/local-models.md).

## Contrat non interactif

Une commande de lecture retourne la projection complète ou une pagination explicite. Une mutation retourne un reçu ; wait suit son opération jusqu’à un état terminal, une erreur ou un timeout local. Un code 0 pour acceptation doit afficher state=accepted et ne peut prétendre à la fin du travail.

Un replay relit l’intention persistée par la première exécution. Le client ne recopie jamais dans une commande existante l’authority_generation annoncée par Hello. StaleFence/STALE_AUTHORITY_GENERATION est restitué tel quel (retry_class=never) avec le lien de récupération. Une nouvelle intention exige la décision de récupération applicable, un nouveau command_id et un lien causal explicite.

Enveloppe JSON : protocol_version, request_id, result ou error, receipt et cursor si pertinent. Les flux watch sont NDJSON versionnés. Les nouveaux champs de réponse sont tolérés ; une version majeure incompatible est refusée. stdout ne contient ni couleurs, ni animations, ni prompt en mode structuré. stderr porte les diagnostics.

| Code proposé | Signification |
| --- | --- |
| 0 | Succès de lecture ou acceptation explicite ; avec wait, fin satisfaisant le contrat. |
| 2 | Usage/entrée invalide, protocole incompatible, ressource introuvable ou masquée (sans distinguer absence et masquage), ou mode interactif requis mais absent. |
| 3 | Authentification ou autorisation refusée. |
| 4 | Conflit de révision, d’idempotence ou de lignée. |
| 5 | Transport/daemon indisponible. |
| 6 | Résultat métier échoué, rejeté ou bloqué, constaté par le reçu ou pendant wait. |
| 7 | Timeout client ou issue restant à inspecter ; command_id/operation_id rendus. |
| 8 | Ressource occupée, quota fournisseur, resynchronisation requise ou défaillance interne ; réessai selon retry_class. |

Correspondance avec l’Error commun : InvalidArgument, ProtocolIncompatible et NotFoundOrHidden → 2, sans distinguer absence et masquage ; AuthenticationFailed, CapabilityDenied et ScopeDenied → 3 ; RevisionConflict, IdempotencyConflict, StaleFence et ContractViolation/IDEMPOTENCY_WINDOW_EXPIRED → 4 ; daemon ou transport absent → 5 ; reçu rejected ou blocked, BudgetExceeded, IsolationUnavailable et autre ContractViolation → 6 ; OutcomeUnknown et timeout client → 7 ; ResourceBusy (dont la saturation ResourceBusy/BACKPRESSURE), RateLimited, ResyncRequired et InternalFailure → 8. Le JSON porte toujours code, reason_code et retry_class.

Une demande de consentement retourne référence du flux, état et instruction exploitable ; elle ne bloque pas un script sur une question masquée. Acceptée (flux user_action_required), elle rend 0 avec l’état et la référence du flux ; 3 est réservé au refus. connector auth recouvre les opérations start/status/cancel/retry du service d’authentification. La CLI peut initier un flux puis le suivre ; le consentement fournisseur reste humain lorsque son protocole l’exige. Notion n’utilise pas de flux OAuth en V1 : son jeton d’intégration interne en lecture seule arrive par secret set sur canal protégé, puis connector test vérifie l’identité du bot (Q-09, [connecteurs](../../specs/connectors.md)). Les limites fournisseur sont conservées.

Les autorisations utilisateur ou politiques préconfigurées déjà applicables valent pour setup et exécution : aucun prompt de confirmation systématique n’est introduit en nonTTY. Si la portée manque, le reçu/erreur décrit la décision requise et son contexte ; une option client ne peut forcer le backend. Changer de mode ou de version crée un nouveau Run autorisé, pas une mutation cachée d’un run actif.

Les secrets arrivent par saisie masquée en TUI, référence de coffre ou canal d’entrée protégé en CLI, jamais par argument littéral. La commande n’affiche pas le secret dans une erreur. Pour les fichiers/flux volumineux, taille et format autorisés sont documentés ; erreur stdin/pipe fermé n’entraîne aucune relance automatique d’effet.

## Interfaces internes de présentation

Le shell TUI reçoit des projections paginées, curseurs et états d’opération ; il rend des actions identifiées avec paramètres typés. Le catalogue d’actions contient libellé, domaine, cible, préconditions, droit requis et aide. Palette, menu et raccourci produisent la même action, avec le même reçu backend. L’état disabled explique une précondition connue sans dévoiler une ressource cachée.

Modes explicites : navigation, formulaire, éditeur, recherche, conversation et PTY attaché. La capture d’entrée appartient à un mode unique ; la touche d’échappement PTY ne devient pas une interruption mission. Les commandes destructives ou d’intervention montrent leur cible et conséquence, puis suivent les autorisations déjà configurées.

Les formulaires guidés et experts consomment les mêmes schémas et gardent le même draft en changeant de densité. Dans le mode supervisé, une décision continue/reconcile/correct/escalate du leader est affichée avec preuve et état d’effet ; seule la commande admissible validée par le harness progresse. Aucun callback de widget ne déclenche de modèle en lisant les logs ou de réparation dans un replay forbidden.

Les mêmes identités, versions, événements et erreurs s’appliquent dans les trois clients. Une préférence de rendu locale peut changer sans requête métier. Aucune préférence de client ne peut modifier un mandat, supprimer un contrôle backend ni transformer une réponse périmée en état confirmé.

## Raccordements vérifiés après revue R2

project create/revise appelle CreateProject/ReviseProject. report request/show appelle CreateReportSnapshot/GetReportSnapshot ; export appelle ExportReport puis ReadArtifact. process acquire appelle AcquireTerminal (variante enregistrée, mode de contrôle demandé) et rend lease_id/fence/lease_expires_at en JSON ; process attach l’emploie en interactif. process input/resize/release exigent --lease-id et --fence et appellent SendTerminalInput, ResizeTerminal et ReleaseTerminal ; process log utilise ReadTerminalLog. Aucune commande CLI n’acquiert ni ne libère un lease implicitement ; un lease non renouvelé expire selon [F011](../F011-terminal-pool/interfaces.md) sans arrêter le processus. Les préférences locales de taille de panneau ne sont pas un resize PTY implicite.

recovery show/reconcile/resolve/resume utilise InspectRecovery, ReconcileAction, ResolveActionOutcome et ResumeRecoveredInvocation. Une résolution affiche classification, preuves, décision et risque ; elle ne convertit jamais un inconnu en succès observé. backup validate/restore utilise ValidateBackup/RestoreBackup et suit la procédure offline exclusive. Tous ces parcours sont accessibles dans la TUI et la GUI selon les mêmes mandats.
