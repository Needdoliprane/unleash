# Matrice Requirement → Architecture → Feature → Test → Evidence

Générée à partir des exigences atomiques des 19 features, puis contrôlée contre leurs fichiers acceptance.md et tests.md. Les preuves EV sont **attendues** ; tous les tests produit sont **not_run** dans cette mission. Le fichier [JSON](traceability.json) fournit la même correspondance pour ingestion par le futur Unleash. Les invariants utilisateur sont couverts séparément dans [invariant-coverage](invariant-coverage.md).

Révision R7. La validation mécanique compare les ensembles, l’unicité des identifiants, les arêtes REQ → AC → T → EV et les textes aux sources des features ; elle contrôle aussi cette projection et les statuts not_run. Convention de ce dossier : chaque chaîne AC-Fnnn-mmm / T-Fnnn-mmm / EV-Fnnn-mmm conserve le même suffixe, sans identifiant implicite. La revue de fond vérifie que le scénario décrit réellement le comportement. Un lien valide ne constitue pas une preuve de fonctionnement du produit.

## Métadonnées obligatoires d'une preuve

Chaque EV produit doit indiquer build/commit, versions, OS/machine, configuration effective, fixture/seed, commande de test du composant (Rust pour le cœur, outil de présentation qualifié si applicable), code de sortie, observations indépendantes, sources/snapshots, hash d'artefacts et limites. Une preuve partielle, inconnue, supprimée ou issue d'un double reste qualifiée comme telle. Les preuves E2E agrègent les sous-preuves des features sans transformer leur absence en réussite.

Couverture extraite : **239 exigences atomiques**. La couverture A–O et des annexes est dans [acceptance-scenarios](acceptance-scenarios.md), [brief-coverage](brief-coverage.md) et le résultat de contrôle dans [document-validation](document-validation.md).
